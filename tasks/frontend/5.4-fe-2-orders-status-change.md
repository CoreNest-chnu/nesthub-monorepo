# Implement order status change with confirmation

**Complexity**: S | **Areas**: web | **US**: 5.4 — Order management | **Estimate**: 1h

## Context

Pairs with `5.4-fe-1-orders-page.md` and depends on `backend/5.4-be-1-orders-endpoints.md`. Adds the per-row interaction that moves an order forward through its lifecycle.

## Granularity note

Small frontend-only task. Kept separate from the list so the read view and the mutation surface can be reviewed in isolation.

## Scope

**In**:
- Per-row `DropdownMenu` showing only valid next statuses for the current order state (mirrors the BE transition map; do not hardcode all statuses)
- `AlertDialog` confirmation before applying the change ("Move order #1234 to PAID?")
- Mutation via `useAdminOrdersControllerUpdateStatus` (Orval-generated)
- Success: invalidate the list query, `toast.success('Status updated')`
- Failure (`400` from invalid transition): `toast.error(serverMessage)` and keep the row's status unchanged

**Out**:
- Reason/notes field for status change
- Bulk status updates

## Acceptance Criteria

- [ ] Dropdown only offers transitions the BE allows (`pending → paid | cancelled`, `paid → shipped | cancelled`, `shipped → completed`, terminal states show no dropdown / a disabled state)
- [ ] After confirmation, the row reflects the new status without a hard reload
- [ ] An invalid transition (if it ever reaches the server) surfaces the BE message in an error toast and the UI stays consistent
- [ ] No state change happens if the user cancels the dialog
- [ ] Dropdown shows a loading state while the mutation is pending
