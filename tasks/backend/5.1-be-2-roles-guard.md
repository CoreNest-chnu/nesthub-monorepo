# Implement RolesGuard and @Roles decorator

**Complexity**: S | **Areas**: api | **US**: 5.1 — Product creation | **Estimate**: 1h

## Context

Currently the API only has `JwtAuthGuard` — there is no enforcement of the `role` field stored on the user. This task adds role-based access control so every admin endpoint can be protected uniformly. All Epic 5 backend tasks depend on this one.

## Granularity note

Pure backend infrastructure task. It has no FE counterpart by design, but it unblocks every other backend task in Epic 5.

## Scope

**In**:
- `@Roles(...roles: Role[])` decorator using `SetMetadata`
- `RolesGuard implements CanActivate` reading metadata via `Reflector`
- Type/constant for roles aligned with the Prisma `Role` enum (`'admin' | 'user'`)
- Unit test verifying admin/non-admin/no-metadata cases

**Out**:
- Applying the guard to admin routes (done in each route's task)
- Anything related to issuing JWTs — role is already embedded by the existing auth flow

## Acceptance Criteria

- [ ] Decorator located at `apps/api/src/auth/decorators/roles.decorator.ts` exporting `Roles(...roles)` and a `ROLES_KEY` constant
- [ ] Guard located at `apps/api/src/auth/roles.guard.ts`; reads handler + class metadata, returns `true` if no `@Roles()` set, else compares `req.user.role`
- [ ] When `req.user` is missing or role doesn't match → guard returns `false` (Nest converts to `403 Forbidden`)
- [ ] Exported from `AuthModule` so any module can import it
- [ ] Unit test (`roles.guard.spec.ts`) covers: no-metadata → allow, matching role → allow, mismatched role → deny, missing user → deny

## Implementation Hints

- Pattern reference: https://docs.nestjs.com/security/authorization (role-based)
- Reuse the `Role` enum from generated Prisma types (`@prisma/client`) to avoid string drift
- Guard order matters — always combine as `@UseGuards(JwtAuthGuard, RolesGuard)` so `req.user` is populated by Jwt before Roles runs
- Existing `JwtAuthGuard` is at `apps/api/src/auth/auth.guard.ts`; place the new files alongside it
